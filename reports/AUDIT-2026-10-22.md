## 2. 问题 A — 飞书推送 GBK 编码崩溃

### 2.1 结论先说

**「同一个地方还会崩」这个假设不成立 —— 10-21 那条日志是修复前的历史记录，修复本身是有效的。**

时间线（`git log` + 文件 mtime 交叉验证）：

| 时刻 | 事件 |
|---|---|
| 10-21 05:30 | 05:30 任务运行。**此时 live checkout 上还没有任何编码修复**（修复 commit 是当天 11:44 写的）→ 崩了 |
| 10-21 11:44 | `0dc5d58` 提交：`safe_print` + `.cmd` 里加 `PYTHONIOENCODING=utf-8` / `PYTHONUTF8=1` |
| 10-21 22:08 | `fb36de0` 提交（gitee-only 日报渲染修复） |
| 10-22 05:30 | 05:30 任务运行 → `[feishu] sent ok, 129 chars` ✅ |

`git show 0dc5d58` 显示的正是：旧代码在 `send_feishu` 里用裸 `print()` 打 openclaw 的输出，而 openclaw 的输出里带 `✅`（`✅ Sent via feishu. Message ID: ...`）→ stdout 是 GBK → `UnicodeEncodeError` → 被 `except Exception` 捕获 → 打印成 `[feishu] exception: ...`。
**注意一个关键事实：10-21 那条日志里 `✅ Sent via feishu` 这行是缺的，而 10-22 是有的 —— 说明 10-21 飞书其实也发成功了，只是最后打印那一步炸了。** 这与 `.cmd` 注释里写的判断一致。

同一份 `logs/gitee-cron.log` 里 10-21 那段是 GBK 乱码（`[prev-index] ???? 385 ??post`），10-22 那段是正常 UTF-8 —— 这本身就是「10-21 那次跑的是旧代码/旧 .cmd」的铁证。

### 2.2 但是：修复**不够彻底**，还有三个真实残留风险

**(A-1) 修复只活在 `.cmd` 包装器里，脚本本身没有兜底。**

`0dc5d58` 只在 `scripts/*.cmd` 里设了环境变量。任何**不是**通过这四个 `.cmd` 启动的路径都会退回 GBK：

- 手动 `python scripts/csdn_incremental.py --all`（人在终端跑）；
- 以后换成 Task Scheduler 直接跑 python、或用 `pythonw`、或 IDE 里点运行；
- `csdn_incremental.py` **完全没有** `safe_print`，它的 `log()`（`csdn_incremental.py:128-135`）直接 `print(line)`，而 line 里全是 `⚠️👁️🆕♻️` → 直接 `UnicodeEncodeError` 崩在抓取中途。

**(A-2) 更危险的是：有两处非 ASCII 的 print 被 `except Exception` 吞掉，会静默丢数据而不是崩。**

- `csdn-monitor-v2.py:451` `print(f"[profile] {username} 页面里找不到'总访问量' ...")` —— 含中文。
  这行在 `fetch_user_total_views` 的 `try` 里（`v2:452-454`），GBK 下会抛 `UnicodeEncodeError` → 被 `except Exception` 吞掉 → `continue` → **`profile_views` 返回 None** → 上层 `v2:592` 退回「文章累加」口径 → total_views 口径在同一天里悄悄切换，用户无感知。
- `csdn-monitor-v2.py:487` `print(f"[stats] html_head={html[:300]!r}")` —— CSDN 页面含中文，`repr()` 保留中文 → GBK 下抛异常 → 被 `v2:489` 的 `except` 吞掉 → **整篇文章的 stats 被判为失败**（`ok=False`），views 不更新（保留旧值）。

也就是说：**在 GBK 环境下，跑一次全量可能悄悄把一堆文章的阅读量冻结在旧值上。** 这是比「打印崩了」严重得多的问题。

**(A-3) `send_feishu` 里的 `safe_print` 是函数内局部定义（`v2:1153-1160`），其它 20 处 print 没有覆盖。**

### 2.3 精确修复方案

**修 1（脚本级兜底，根治）—— `scripts/csdn-monitor-v2.py`，在第 45 行 `import requests` 之后插入：**

```python
# ---------- stdout 编码兜底 (必须在 import 之后, 且在任何 print 之前) ----------
# 计划任务/手动运行时 stdout 可能是 GBK(936), 非 ASCII 会抛 UnicodeEncodeError。
# 在 fetch_user_total_views / fetch_article_stats 里那个异常会被 except 吞掉,
# 静默丢数据 (profile_views 变 None / 整篇 stats 判失败), 比崩掉更糟。
def safe_print(msg):
    try:
        print(msg)
    except UnicodeEncodeError:
        try:
            print(msg.encode("ascii", "replace").decode("ascii"))
        except Exception:
            pass


try:
    sys.stdout.reconfigure(encoding="utf-8", errors="replace")
    sys.stderr.reconfigure(encoding="utf-8", errors="replace")
except Exception:
    pass
```

**修 2 —— 同样一段插入 `scripts/csdn_incremental.py` 第 84 行 `import requests` 之后**（该文件完全没有 safe_print），并把 `csdn_incremental.py:130` 的 `print(line, flush=True)` 改成 `safe_print(line)`。

**修 3 —— 把 `v2` 里所有可能含非 ASCII 的 print 换成 `safe_print`：** 行 `443`(`[profile] ... HTTP`)、`446`、`451`、`453`、`467`、`471`、`485`、`486`、`487`、`490`。

**修 4 —— 删除 `v2:1153-1160` 的函数内局部 `safe_print` 定义**，改用模块级的（否则定义重复、后面加的 print 容易漏改）。

**修 5（可选，防御性）—— 四个 `.cmd` 里的 `set PYTHONIOENCODING=utf-8` / `set PYTHONUTF8=1` 保留**（双保险），但注释改成「兜底，脚本内已有 reconfigure」。

### 2.4 回归验证

1. `python -c "import subprocess,sys; print(sys.stdout.encoding)"` 在计划任务里 → 期望 `utf-8`；即使不是，`safe_print` 也不应抛。
2. 用 GBK 环境模拟：在 cmd 里 `set PYTHONIOENCODING=gbk` 后跑 `python scripts/csdn_incremental.py --student 庞嘉良 --dry-run` → 期望：日志里的 emoji 变成 `?` 而不是抛 `UnicodeEncodeError`；`data.json` 不被改动（dry-run）。

## 4. 问题 C — views 双口径不一致

### 4.1 两个口径分别是什么

| 字段 | 来源 | 计算方式 | 性质 |
|---|---|---|---|
| `profile_views` | CSDN 个人主页侧栏「总访问量」 | `csdn_stats.parse_profile_views()`（`csdn_stats.py:205-237`）解析 `user-profile-statistics-views` 容器 | **空间累计计数器，实时** |
| `article_views_sum` | 385 篇文章详情页 | 每篇 `meta description` 里的「文章浏览阅读N次」求和（`csdn_stats.py:116-180`） | **采样快照，被限流/轮转影响** |
| `total_views` | 三源择优 | `v2:592-600` / `csdn_incremental.py:468-476`：**profile 优先**，profile 拿不到才退到 article 累加 | 现在 34/34 全是 `profile` |

### 4.2 差值是什么造成的（**用数据定量，不用猜**）

我拉了 `history-real/2026-10-21.json` 与 `2026-10-22.json` 的两次快照做对比：

| 时刻 | Σprofile | Σarticle_views_sum | 差 |
|---|---|---|---|
| 10-21 12:06（增量） | 63,824 | 63,135 | **689** |
| 10-22 00:24（增量） | 65,777 | 63,392 | **2,385** |

**12 小时内：profile 涨了 +1,953，文章累加只涨了 +257 —— 87% 的「增长」不是文章阅读带来的。**

再把差值按学生拆开（10-22 00:24）：

- 34 个学生 **全部** `profile ≥ article_views_sum`，没有例外；
- 其中 8 个学生 `差值 == 文章数`（差值完全等于 post_count，如 王翼洲 12 篇差 12、武明光 10 篇差 173 不符、韩博 15 篇差 88）；更准确地说：8 人差值恰好 = 文章数，其余人的「超出部分」在 0~173 之间随机分布，合计正好 2,000；
- 这 12 小时里差值增长最多的是 王明硕(+175)、郑翔(+169)、杨智(+161)、季政科(+145)、陈艳(+128)；而 王森/王润田/赵丁闫/王翼洲 四人 **12 小时内差值一点没变**。

**结论（可由上面的数据直接推出）：**

1. `总访问量` 是**博客空间的累计计数器**，它比「文章阅读数之和」多出来的部分包含：① 主页/空间访问；② **我们没有重抓到的那些文章的阅读增长**。
2. 第二点可以用 庞嘉良 验证：他一共 6 篇文章，10-22 那次增量把 6 篇**全部重抓了**（日志：`🆕新0 全抓0 | ↻最近更新4 轮转2 | ♻️复用0`），文章累加 989→1013（+24），但 profile 1003→1089（**+86**），差值从 14 涨到 76。既然他的 6 篇文章全刷新了，那多出来的 62 次**不可能是未刷新的文章**，只能来自**主页访问 / 空间 PV**（或 CSDN 对重复访问的去重差异：文章「阅读数」按独立访客去重，空间「总访问量」按 PV 累加）。
3. 反过来，陈艳/王明硕这类「差值猛涨」的，profile 涨 148 而刷新的文章只涨 20，说明另外 128 次落在**我们这轮没重抓的文章**上（增量模式每天只重抓 4+2=6 篇，平均 11.3 篇/人 ⇒ **约一半的文章每 2~4 天才刷新一次**）。

**所以：两个数都不是「错」的，但它们回答的是不同问题：**

### 5.2 根因与逐条回答

#### (D-1) 521 的重试/退避**基本没生效** —— 真 bug

`csdn_incremental.py:147-154`：

```python
if r.status_code in (521, 403, 429):
    LIMITER.escalate(1.5)
    LIMITER.penalize(5.0 + attempt * 5)     # ← 第 1 次只冷却 5 秒
    last_err = f"HTTP {r.status_code}"
    if attempt < retries:
        continue
```

CSDN 的 521 是 **IP 级风控**，实测封禁持续**分钟级**，不是 5 秒。所以 6/7 次重试必然再被拦 —— 实证：6 篇 521 文章两次尝试全挂，只有 1 篇侥幸通过。
**代价是双重的**：既没拿到数据，又白烧了一个请求（438 里至少有 6 个是纯浪费）。

还有一个次要问题：`penalize()` 在**最后一次尝试时也会执行**（没有 `if attempt < retries` 保护），等于最后还要给全局限流器加 5 秒冷却，白白拖慢后面的学生。

**修复（`csdn_incremental.py:147-154`）：**

```python
            if r.status_code in (521, 403, 429):
                # 撞风控: CSDN 的 521 是 IP 级封禁, 实测持续数分钟,
                # 5 秒后立刻重试必然再被拦 (2026-10-22 实测 6/7 篇如此)。
                LIMITER.escalate(1.5)
                last_err = f"HTTP {r.status_code}"
                if attempt < retries:
                    LIMITER.penalize(45.0)      # 真的退避: 45 秒冷却
                    log(f"    ⚠️ {last_err} (风控), 45s 冷却后重试 url={url[:70]}")
                    continue
                LIMITER.penalize(10.0)          # 放弃这一篇, 但别拖累后面
                log(f"    ⚠️ {last_err} (风控), 放弃本篇 url={url[:70]}")
```

配套：`MAX_CONSECUTIVE_FAILURES = 5`（`csdn_incremental.py:125`）保持不变；被放弃的文章**保留旧值**（见 D-2），明天轮转会再试。
**注意副作用**：45 秒冷却 × 6 次 = 多花 4.5 分钟，整轮从 24 分钟变 29 分钟，仍远小于任务上限（Task Scheduler 设的是 2 小时），可以接受。
如果 Ma 不想要这个延迟，替代方案是**521 直接不重试**（`retries=0`），把失败留给第二天的轮转 —— 一天的阅读量延迟无关紧要。

`data.json.last_fetch_meta` 现在是 05:30 那次 gitee-only 的产物：

```json

 "method_breakdown": {"csdn_html": 0, "csdn_rss": 0, "gitee_api": 0, "gitee_html": 0},

 "rate_limiter": {"waits": 0, ...},
 "success_count": 66, "fail_count": 2,

```

而 00:00 那次增量的真实数字是：**438 个请求、耗时 1462 秒、178 篇重抓、7 篇失败**。**这些全被覆盖没了。**

三个叠加的原因：
