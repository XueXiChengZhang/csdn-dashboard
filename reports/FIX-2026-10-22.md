### 4.3 为什么保留全量而不是改成限范围

任务文件给了两个选项：(a) 改成限范围（`--recent 8 --rotate 4`），(b) 保留全量 + 回滚。我们选 **(b)**，理由：

1. 限范围只是**回避**问题：全量本来能修的数据漂移（老文章 views 停在几周前）不会被修；真出事时数据照样是错的，而且错得没人知道。
2. 限范围解决不了真正的风险点：这次 7 次暴跌都是**别的任务**（05:30 gitee-only）写坏了 data.json，不是全量任务写坏的。缩。全量并不能防止别人覆盖。
3. 真正的解法是**写入前的校验 + 可回滚**（R7 做的），它对「任何原因」导致的数据残缺都有效，而限范围只对「全量跑太狠」这一种原因有效。
4. 全量有独立价值：它是唯一能修复「轮转一圈漏掉的文章 / 已删除的文章」的机制。砍掉它等于用一个已知的、还没修的故障换一个已知的收益。

### 4.4 阈值怎么定的（避免误报）

- 60% 而不是 30%：`apply_data_protection` 的 C 臂只挡「总阅读 < 上次 30%」，10-12 那次 -100% 能挡住，但 10-01 的 -39% 挡不住。60% 兼顾「39% 这种量级的真实故障」和「正常波动」。
- 60% 不会误报口径切换：实测 profile 总访问 65,777 vs 文章累加 63,392，只差 3.6%，远在 40% 的余量内。
- 学生级 20% + 单人掉量 50%：单人掉一半才算「失败」，避免某一个人被软反爬就误伤全班。
- 文章数 70%：文章数是硬指标，掉 30% 一定不正常。

### 4.5.2 端到端演练（备份 → 写坏 → 拦截 → 回滚 → 放行）

在临时目录搭一个完整「仪表盘」环境（`data.json` + `cache/csdn/snapshot.json` + `history-real/`），
用真实数据跑完整链路：

```
初始总阅读 65,777
  ↓ backup                → cache/backup/2026-10-22T16-46-56/{data.json, cache/csdn/snapshot.json, manifest.json}
  ↓ 模拟跑坏(打 3 折)     → 总阅读 19,717
  ↓ check                 → rc=1  ← 正确拦截
  ↓ rollback              → rc=0  恢复 65,777（与原始一致）
  ↓ check (恢复后再校验)  → rc=0  ← 正确放行
```

结论：安全网是**闭环**的，不是摆设——跑坏了能自动退回，退回后数据与跑之前**一字不差**。
