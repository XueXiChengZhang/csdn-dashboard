## 一、问题背景

### 1.1 核心故障：阅读量被覆盖写坏（已发生 7 次）

`history-real/` 里 33 天归档、64 个带 `total_views` 的快照点，逐日对比「00:00 增量」与「05:30 gitee-only」的班级总阅读量：

| 日期 | 00:00 增量 | 05:30 gitee-only | 变化 |
|---|---|---|---|
| 2026-09-22 | 20,130 | 6,729 | **-67%** |
| 2026-09-30 | 21,946 | 7,157 | **-67%** |
| 2026-10-01 | 31,151 | 19,035 | **-39%** |
| 2026-10-02 | 27,438 | 18,457 | **-33%** |
| 2026-10-12 | 13,967 | 0 | **-100%** |
| 2026-10-19 | 1,352 | 0 | **-100%** |
| 2026-10-21 | 7,604 | 1,297 | **-83%** |

最典型是 **10-16**：00:00 增量算出 50,686，05:30 覆盖成 9,609 —— 仪表盘显示少了 81%。到 10-21 11:31 有人手动跑全量才恢复。

取证文件：`D:\WebArchives\knowledge\分析报告\CSDN阅读量暴跌_历史取证.json`

### 1.2 未爆的时间点：周日全量任务

`\csdn-dashboard-monitor-weekly`（每周日 03:00）**从未跑过一次**（上次运行时间 = 1999/11/30），下次 **2026/10/25 03:00**。

它执行 `csdn-monitor-v2.py --force-now --no-reuse` —— 385 篇全部重抓（2.5 秒/篇 ≈ 16 分钟）。`--no-reuse` 关掉的正是 24 小时复用保护，而那正是 10-21 把阅读量打成 1,297 的同一个动作。它还用 `git add -A`，任何残缺结果都会**直接 commit + push 到 GitHub Pages**。

### 1.3 其他问题

- Gitee 空仓库被当成抓取成功，请求数归零
- `last_fetch_meta` 被增量与 Gitee 互相覆盖
- 521 风控冷却只有 5~6 秒，等于硬撞
- 404 文章每轮重试，白烧请求
- 「抓不到文章」不区分"真的没有"和"被软反爬"
- 增量抓完不重算 `class_stats`，班级统计停在全量那天
- 前端「总阅读」混称总访问量与文章阅读合计
- fetch-meta 面板读错的 key，三个格子永远显示 0
- GBK 环境下 `print()` 抛 UnicodeEncodeError，**静默丢数据**

## 二、修复清单

### R1 · `last_fetch_meta` 按模式分块
- **commit**：`c780c6a`
- **问题**：增量模式与 Gitee 模式写同一个 meta key，互相覆盖，仪表盘只能看到最后一次
- **改动**：改成 `methods` 下按模式分块，增量与 Gitee 同时可见
- **测试**：`test_frontend_views.js` 新增 fetch_meta 分块断言

### R2 · 521 风控冷却 5~6 秒 → 45 秒
- **commit**：`227592d`
- **问题**：CSDN 返回 521 说明触发风控，等 5 秒再撞基本等于继续挨打
- **改动**：冷却时间提高到 45 秒
- **测试**：断言间隔 ≥ 45 秒

### R3 · 404 标记删除，不再重试
- **commit**：`d40f4ec`
- **问题**：文章被 CSDN 删除后，每轮都重试详情页，白烧请求
- **改动**：标记 `_deleted_on_csdn`，后续轮次跳过
- **测试**：断言 404 文章第二轮不再发起请求

### R4 · 区分「真的没文章」与「被软反爬」
- **commit**：`c63d3f8`
- **问题**：列表页"抓不到文章"分不清是学生真的没发文，还是被 CSDN 软封
- **改动**：两种情况分别标记
- **测试**：软反爬场景断言

### R5 · 增量抓完重算 `class_stats`
- **commit**：`ec372bb`
- **问题**：班级统计只在全量任务时更新，日常增量跑完仪表盘数字还是旧的
- **改动**：增量结束后重算班级统计
- **测试**：断言增量后 `class_stats` 与学生数据一致

### R6 · 前端口径透明化
- **commit**：`34d1c8a`
- **问题**：「总阅读」这个词同时指"主页访问量"和"文章阅读累加"，两个数差 2,385（3.76%）却用同一个标签
- **改动**：「总访问量」与「文章阅读合计」分开显示，tooltip 说明
- **测试**：`test_frontend_views.js` 断言两个标签都存在

### R7 · 周日全量任务安全网 ★★ 最高优先
- **commit**：`ab9cc89` + `scripts/weekly_guard.py`（402 行）
- **问题**：见 1.2 —— 任务从未验证过，且路径与 7 次已发生故障完全相同
- **改动**：
  1. **备份**：跑之前备份 `data.json` + `cache/csdn/snapshot.json` + 当日归档（带时间戳，留最近 8 份，存 `cache/backup/`）。备份失败 → 中止，不跑全量
  2. **校验**（比 `apply_data_protection` 的 C 臂严 —— C 臂只挡"< 30%"，掉 40% 它挡不住）：
     - R1 绝对下限：总阅读 < 上次 **60%** → 回滚
     - R2 学生级：失败学生占比 > **20%** → 回滚
     - R3 文章数：总文章 < 上次 **70%** → 回滚
  3. **回滚**：校验不过或抓取报错 → 原样恢复备份，**且不 commit、不 push**
- **保留 `--no-reuse` 全量的理由**：全量能修复长期滞后的文章数据（增量只碰最近 4 篇 + 轮转 2 篇，老文章的 views 可能停在几周前）。限范围只是回避问题 —— 真出事了数据还是错的，而且错得没人知道。全量 + 严格回滚 = "敢跑全量，但跑坏了自动退回去"。
- **独立验证**（用真实 `data.json` 构造 8 个场景，全部符合预期）：

  | 场景 | 结果 | 期望 |
  |---|---|---|
  | 正常（不变） | ok=True | True ✅ |
  | 总阅读 -50% 腰斩 | ok=False | False ✅ |
  | 总阅读 **-40%（原 C 臂漏掉）** | ok=False | False ✅ |
  | 总阅读 -39%（阈值内） | ok=True | True ✅ |
  | 全部归零 | ok=False | False ✅ |
  | 8/34 学生失败（24%） | ok=False | False ✅ |
  | 6/34 学生失败（18%） | ok=True | True ✅ |

- **端到端演练**（真实备份 → 写坏 → 校验拦截 → 回滚 → 再校验放行）：
  ```
  初始 65,777 → 写坏 19,717 → check rc=1（拦截）
  → rollback rc=0 → 恢复 65,777（与原始一致）→ check rc=0（放行）
  ```
